## 一、这个想法从哪来

今天在整理电脑上的 skill 时冒出来的。当时在做两件事：

1. 盘点自己机器上到底有哪些 skill（27 个）
2. 想挑几个发给在 UCB 读 CS 的朋友

盘点的过程中发现一个问题：**skill 越来越多，但没人告诉「什么任务该用哪个」**。而且更进一步——**一个复杂任务本来就不该由一个 agent 单打独斗**。

---

## 二、核心构想（原话整理）

### 构想 A：技能分库

> 「把这些 skill 再分类，这样的话，每个任务，你可以调用适合的 skill 去做」

- 所有 skill 按**任务类型**分类
- 给定任务 → 能快速定位到该用哪个 skill
- 形成一张**调度表**

### 构想 B：多 Agent 分工

> 「再创造多个 agent，让他们每一个使用一个方面的 skill，然后一起做事情，这样更加的精准」

- 一个任务拆成多步
- **每一步用不同数量的 agent**
- **每个 agent 配专属 skill**（不是所有 agent 共用一套）

### 构想 C：Agent 之间交流 + Leader 决策

> 「还可以让他们自己谈话，交流……第一步大概完成了，他们决策，各自汇报结果，有一个 leader，知道我的审判标准，或者那个 leader 就是我，决定要不要进行第二步」

- agent 各自干完 → **汇报结果**
- **Leader** 汇总 + 决策
- Leader **掌握「我的审判标准」**（关键：标准是我的，不是 agent 自己定的）
- **Leader 可以是我本人**（人类在环）

### 构想 D：失败就回炉 → 先找错，再改，再创新

> 「不行的话就重复第一步，先寻找错误，然后再改，再创新，类似于这种循环，直到第二步开始，最后第三步完成，各自分工，各自拿专属 skill」

- 不通过 → **回到该步骤重做**
- 重做的顺序有讲究：**先找错 → 再改 → 再创新**（不是直接重来）
- 循环直到通过，才进入下一步

## 三、这个流程长什么样

```
                    ┌─────────────────────────────┐
                    │  Step 1                      │
                    │  ┌────┐ ┌────┐ ┌────┐        │
                    │  │A1  │ │A2  │ │A3  │  n 个  │
                    │  │skill│ │skill│ │skill│ agent │
                    │  └────┘ └────┘ └────┘        │
                    └──────────┬──────────────────┘
                               │ 各自汇报
                               ▼
                    ┌─────────────────────────────┐
                    │      Leader（或我本人）       │
                    │  按【我的验收标准】判定        │
                    └──────┬──────────────┬───────┘
                       不通过 │              │ 通过
                              ▼              ▼
              ┌───────────────────────┐   ┌─────────────┐
              │ 回炉循环               │   │  Step 2     │
              │ ① 找错（critic）       │   │  （不同数量  │
              │ ② 改（revise）         │   │   的 agent） │
              │ ③ 创新（re-imagine）   │   └──────┬──────┘
              └───────────┬───────────┘          │
                          └──── 回到 Step 1 ──────┘
                                                  ▼
                                            Step 3 → 完成
```

**三个我认为最关键的设计点：**

1. **验收标准是「我的」** —— 不是 agent 自己定的。这决定了整套系统的方向不跑偏。
2. **失败后的三步顺序** —— 先找错、再改、再创新。直接重来是浪费，跳过找错就直接改是瞎改。
3. **每一步的 agent 数量和技能组合可以不同** —— 不是固定团队，是按需编队。

## 四、为什么我觉得这事有意思

### 1. 它解决了一个真问题

现在的 AI 用法基本是「一个模型回答一个问题」。复杂任务要么靠人拆，要么让它一口气做完（然后质量不稳）。

**这套流程把「拆解 + 分工 + 验收 + 迭代」显式化了。**

### 2. 它把「我的标准」放在中心

大多数 AI 工作流让人去适应工具。这个反过来——**工具围着我的验收标准转**。

### 3. 它天然适合我的场景

我手上的活（论文实验、策略回测、竞赛方案）都是**多步骤、有明确验收标准、需要反复迭代**的。特别是我做量化回测时，本来就是「跑→看结果→不行就改→再跑」的循环。

### 4. 如果做出来，是个能开源的东西

**需求是通用的**——任何做复杂任务的人都需要。而且比单个工具更有想象空间。

## 八、【2026-09-29 调研结论】已有方案 vs 真正空白

> 调研方法：GitHub REST API + 官方文档抓取 + 本机 Claude Code v2.1.222 二进制核验

### 8.1 已被解决的（**不要重造**）

Claude Code 官方已有三层多 agent 能力：

| | Subagents | Agent teams | **Workflows** |
|---|---|---|---|
| 谁决定下一步 | Claude 逐轮 | lead 逐轮 | **脚本** |
| 中间结果存哪 | 上下文 | 共享 task list | **脚本变量** |
| 规模 | 每轮几个 | 几个长驻 | **几十到几百** |

| 我的构想 | 现成方案 |
|:--|:--|
| 任务分多步 | 官方 Dynamic Workflows |
| 每步不同数量 agent | 官方 `pipeline()` / `parallel()` |
| **每个 agent 配不同 skill** | 官方 subagent **`skills:` 预加载字段** |
| 各自汇报、Leader 汇总 | subagent 返回值 / Agent Teams 的 `SendMessage` |
| **Leader 验收** | 官方 `agent(prompt, {schema})` **自动校验+重试** |
| 不通过回到该步 | 官方 `ralph-loop`；论文 Reflexion |
| agent 互相交流 | 官方 Agent Teams（实验性） |

**官方 `/deep-research` 内置 workflow = 「扇出→交叉核验→投票→过滤」的参考实现。**

同类开源：`obra/superpowers`(292k★)、`cft0808/edict`(17k★，三省六部制)、
`abidwaqar/AI-Judgment-Orchestration`(14★，流程几乎一一对应)、
`LeoStehlik/proof-loop`(11★，AC 冻结+独立验证最严谨)。

### 8.2 三个真实空白（★ 其中 1 个是我的原创）

**🎯 空白 1（原创）：三阶段失败恢复「找错→改→创新」**

现有方案**全部只有两阶段**：

```
Reflexion    ：执行 → 反思 → 重试
Self-Refine  ：生成 → 自批判 → 修订
proof-loop   ：验证 → 修 → 再验证
ralph-loop   ：不通过就重跑
```

**我要的三阶段：**
```
① 找错（critic，只找错）
② 改  （reviser，只改）
③ 创新（都不行 → 放弃修补，换方案重来）
```

> **第三阶段在任何论文/开源项目里都没有对应实现。**
> 最接近的是 Tree-of-Thoughts 的「回溯换分支」，但那是**搜索**，不是**「修不好就重新发明」**。

**空白 2：声明式「一步一策」配置**

现有方案要么固定团队（三省六部写死 12 角色），要么手写脚本。
**没有声明式表达「Step 2 用 3 个 agent 加载 skill A/B/C」的方式。**

**空白 3：验收标准做成可机检对象**

`proof-loop` 最好，但仍是纯文本 + 人工检查。
**把 AC 结构化成 `schema`，让 runtime 强制执行判决**——没人做。

### 8.3 定位结论

**不做「又一个编排框架」**（CrewAI 59k★、AutoGen 61k★ 已经挤满）。

**做薄薄一层，架在官方原语之上：**

```
我的 skill = 官方 Workflow + 三个填空
  ├─ 声明式「一步一策」配置
  ├─ 三阶段失败恢复（找错→改→创新）← 原创
  └─ 验收标准 schema 化
```

**卖点**：别人告诉你「多做几轮」，我告诉你「第几轮该换思路」。

### 8.4 风险提醒

- workflow 脚本**必须确定性**（禁 `Math.random()`/`Date.now()`）→ 动态决定 agent 数量要靠脚本逻辑算，不能随机
- **Agent Teams 是实验性的**，官方明说 session 恢复/任务协调/shutdown 有问题
- 官方 workflow 的适用边界是「一次几十到几百个 agent」的大任务；**中小规模用 subagent + skill 就够**
- **先自己用一个月**，用出真效果再开源。自己都不用，别人不会用。
