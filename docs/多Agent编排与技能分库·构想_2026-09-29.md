## 一、这个想法从哪来

今天在整理电脑上的 skill 时冒出来的。当时在做两件事：

1. 盘点自己机器上到底有哪些 skill（27 个）
2. 想挑几个发给在 UCB 读 CS 的朋友

盘点的过程中发现一个问题：**skill 越来越多，但没人告诉「什么任务该用哪个」**。而且更进一步——**一个复杂任务本来就不该由一个 agent 单打独斗**。

---

## 二、核心构想（原话整理）

### 构想 A：技能分库

> 「把这些 skill 再分类，这样的话，每个任务，你可以调用适合的 skill 去做」

- 所有 skill 按**任务类型**分类
- 给定任务 → 能快速定位到该用哪个 skill
- 形成一张**调度表**

### 构想 B：多 Agent 分工

> 「再创造多个 agent，让他们每一个使用一个方面的 skill，然后一起做事情，这样更加的精准」

- 一个任务拆成多步
- **每一步用不同数量的 agent**
- **每个 agent 配专属 skill**（不是所有 agent 共用一套）

### 构想 C：Agent 之间交流 + Leader 决策

> 「还可以让他们自己谈话，交流……第一步大概完成了，他们决策，各自汇报结果，有一个 leader，知道我的审判标准，或者那个 leader 就是我，决定要不要进行第二步」

- agent 各自干完 → **汇报结果**
- **Leader** 汇总 + 决策
- Leader **掌握「我的审判标准」**（关键：标准是我的，不是 agent 自己定的）
- **Leader 可以是我本人**（人类在环）

### 构想 D：失败就回炉 → 先找错，再改，再创新

> 「不行的话就重复第一步，先寻找错误，然后再改，再创新，类似于这种循环，直到第二步开始，最后第三步完成，各自分工，各自拿专属 skill」

- 不通过 → **回到该步骤重做**
- 重做的顺序有讲究：**先找错 → 再改 → 再创新**（不是直接重来）
- 循环直到通过，才进入下一步

## 三、这个流程长什么样

```
                    ┌─────────────────────────────┐
                    │  Step 1                      │
                    │  ┌────┐ ┌────┐ ┌────┐        │
                    │  │A1  │ │A2  │ │A3  │  n 个  │
                    │  │skill│ │skill│ │skill│ agent │
                    │  └────┘ └────┘ └────┘        │
                    └──────────┬──────────────────┘
                               │ 各自汇报
                               ▼
                    ┌─────────────────────────────┐
                    │      Leader（或我本人）       │
                    │  按【我的验收标准】判定        │
                    └──────┬──────────────┬───────┘
                       不通过 │              │ 通过
                              ▼              ▼
              ┌───────────────────────┐   ┌─────────────┐
              │ 回炉循环               │   │  Step 2     │
              │ ① 找错（critic）       │   │  （不同数量  │
              │ ② 改（revise）         │   │   的 agent） │
              │ ③ 创新（re-imagine）   │   └──────┬──────┘
              └───────────┬───────────┘          │
                          └──── 回到 Step 1 ──────┘
                                                  ▼
                                            Step 3 → 完成
```

**三个我认为最关键的设计点：**

1. **验收标准是「我的」** —— 不是 agent 自己定的。这决定了整套系统的方向不跑偏。
2. **失败后的三步顺序** —— 先找错、再改、再创新。直接重来是浪费，跳过找错就直接改是瞎改。
3. **每一步的 agent 数量和技能组合可以不同** —— 不是固定团队，是按需编队。

## 四、为什么我觉得这事有意思

### 1. 它解决了一个真问题

现在的 AI 用法基本是「一个模型回答一个问题」。复杂任务要么靠人拆，要么让它一口气做完（然后质量不稳）。

**这套流程把「拆解 + 分工 + 验收 + 迭代」显式化了。**

### 2. 它把「我的标准」放在中心

大多数 AI 工作流让人去适应工具。这个反过来——**工具围着我的验收标准转**。

### 3. 它天然适合我的场景

我手上的活（论文实验、策略回测、竞赛方案）都是**多步骤、有明确验收标准、需要反复迭代**的。特别是我做量化回测时，本来就是「跑→看结果→不行就改→再跑」的循环。

### 4. 如果做出来，是个能开源的东西

**需求是通用的**——任何做复杂任务的人都需要。而且比单个工具更有想象空间。

## 六、我打算怎么做

**分三层，从下往上建：**

### 第一层：技能分库（马上能做）

把 27 个 skill 按任务类型分类，做成一张调度表。

```
写作类     → docx / doc-coauthoring / research-writing-skill
数据类     → xlsx / office-excel
阅读类     → pdf / pdf-to-markdown
科研配图   → scipilot-figure-skill
量化       → （待建）cn-stock-data
...
```

### 第二层：专用 agent 定义

每个 agent = 一个角色 + 指定技能 + 明确职责。
比如 `critic`（只找错，不改）、`reviser`（只改，不找错）、`leader`（只判定，不动手）。

### 第三层：编排流程

把「分工 → 汇报 → 判定 → 回炉/前进」写成可复用的流程。
